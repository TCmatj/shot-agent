# 代码自动 Review

## Review 立场

优先关注正确性、回归风险、可维护性、安全问题、数据丢失、用户可见行为和缺失验证。先列问题，再写总结。

## Review 范围

review 实际变更文件和 diff。可用时优先参考：

- `git status --short`
- `git diff`
- `git diff --staged`
- 相关测试、构建或 lint 输出
- review 远端 PR 时的 PR diff 和评论

## 检查清单

重点检查：

- 正确性缺陷和边界场景问题
- UI 行为回归、布局重叠或不可访问控件
- 缺失的加载、空态、错误态和取消态
- 不安全的文件、网络、认证、token 或密钥处理
- 依赖、构建或配置漂移
- 与变更风险不匹配的测试或验证缺口
- 意外提交的无关变更、生成文件、日志或本地临时文件
- `README.md` 或 `README.en.md` 变更时的中英文同步
- review commit 或 PR 时，检查是否符合提交和 PR 规范

## 输出格式

如果发现问题，先按严重程度列出：

```markdown
发现问题：

- [P1] 标题
  文件：path/to/file:line
  问题：...
  建议：...

开放问题：

- ...

验证情况：

- ...
```

如果没有发现问题，明确说明，并补充剩余风险或缺失验证：

```markdown
未发现阻塞问题。

验证情况：

- ...

剩余风险：

- ...
```

## 严重级别

- `P0`：会导致数据丢失、安全事故、生产不可用，必须立即处理
- `P1`：高概率功能错误、主要流程不可用、明显回归，合并前必须处理
- `P2`：边缘问题、维护性风险、缺少关键验证，建议合并前处理
- `P3`：小问题、命名、可读性、非阻塞改进

## 规则

- 不要把问题埋在长总结后面。
- 不要只根据意图认可变更，必须查看 diff 或命令输出。
- 当聚焦修复足够时，不要要求大范围重写。
- 不要把纯风格偏好当作阻塞问题。
- 如果证据不足，明确说明哪些内容没有验证。
